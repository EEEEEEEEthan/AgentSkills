# 禁止 set_script

## 核心规则

**永远不要用 `set_script()` 在运行时替换节点脚本。** 它是技术债的温床。

## 为什么

1. **破坏 @onready**：`@onready` 只在节点首次 `_ready` 时求值。`set_script` 后新脚本的 `@onready` 不会被重新执行，所有延迟初始化引用一律为 null——必须改用延迟 getter 或手动注入，代码腐化。

2. **状态残留**：旧脚本的实例变量（`var`、`signal` 连接）仍挂在节点上。新旧脚本的属性名冲突时，旧值静默存活，调试时极难定位。

3. **类型系统失明**：`as PlanetStory` 等强转在 `set_script` 之前或之后都可能失败，因为引擎的运行时类型在 `set_script` 瞬间切换，静态分析工具完全追踪不到。

4. **_ready 时序炸弹**：`set_script` 会触发 `_ready`，如果此时节点已在树中，`_ready` 在不完整状态下执行；如果不在树中，`@onready` 全部为 null。无论哪种分支都需加防护，防护一多就散落成垃圾代码。

## 正确替代

| 想做的事 | 正确做法 |
|----------|----------|
| 派生场景需要不同行为 | 在 .tscn 里直接挂不同脚本（builtin 或 ext），让编辑器在实例化时绑定 |
| 运行时切换行为 | 用组合：节点始终挂基类脚本，通过 `@export` 或子节点注入策略对象 |
| 壳/容器需要注入外部脚本 | 让脚本声明在数据侧（.tscn），容器只读取并调用，不替换宿主 |

## 一句话

**脚本归属在 .tscn 里声明，运行时只读不写。**
