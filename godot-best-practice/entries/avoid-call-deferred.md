# 禁止 call_deferred

## 核心规则

**永远不要用 `call_deferred()`。** 除非你已穷尽所有同步方案且能清楚写下为什么必须延一帧。

## 为什么

1. **一帧幽灵状态**：`call_deferred` 把操作推迟到当前帧末尾（idle 阶段）。调用点和执行点之间，场景树处于中间态——节点可能已 add_child 但未 ready、父节点正在重组、引用可能悬空。任何依赖"调用后状态已更新"的代码都会踩坑。

2. **时序不可控**：同一帧里多个 `call_deferred` 的执行顺序取决于注册顺序，跨脚本的注册顺序无法保证。A defer 的回调可能依赖 B defer 的结果，但 B 不一定先执行。

3. **掩盖架构问题**：90% 的 `call_deferred` 是在绕开 `_ready` 时序问题——"节点还没 ready 所以我延一帧"。这说明场景树的构建顺序本身有问题，正确做法是调整树结构或用信号/回调，而不是把时序缺陷藏在 defer 里。

4. **调试黑洞**：deferred 调用不出现在正常调用栈里，报错时行号跳到 idle 阶段，与触发点完全脱节。调试器断点也不会在 `call_deferred` 行命中，必须手动追。

5. **组合爆炸**：一个 defer 引发另一个 defer，链条越长状态越不可预测，最终变成"只有跑起来才知道对不对"。

## 正确替代

| 想做的事 | 正确做法 |
|----------|----------|
| 等节点 ready 再操作 | 用 `await node.ready`（如果节点已在树中则立即返回），或在 `_ready` 里直接操作 |
| 等帧末布局稳定 | 显式调 `reset_size` / `update_minimum_size` 等同步布局方法 |
| 父节点构建时需操作子节点 | 让子节点在 `_ready` 里主动注册自己，父节点不假设子节点已存在 |
| 跨节点协调 | 信号：子节点 ready 后 emit，父节点监听 |

## 真正需要 defer 的极少数场景

- 引擎 bug 导致必须延一帧才能正确访问（应记录 bug 编号）
- 必须在物理帧之前/之后操作且无法用 `_physics_process` 替代

上述场景必须在代码旁写注释说明原因。

## 一句话

**先修树结构，再用信号；call_deferred 是最后手段，不是默认选项。**
