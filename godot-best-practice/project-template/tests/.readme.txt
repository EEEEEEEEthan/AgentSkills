tests/ 怎么组织、怎么跑、什么能进档

三档测试（.engine_test.py，条目上限、并发与时间上限都写死在该文件里，不读 project.godot）

a 档 `--id <条目>...`（不给参数即 smoke）
  扫描：只跑点名的条目。并发默认 4（--jobs 可改）。单项上限 30 分钟，无整轮上限。
  用途：每轮开发后的自测。

b 档 `--ci`
  扫描：本层一层、文件名不以 _ 开头的全部条目。并发限死 4（给 --jobs 直接退出 2）。
  单项上限 30 分钟，整轮上限 5 分钟。用途：提交 / MR / CI。

c 档 `--full`
  扫描：本层一层全部条目（含 _ 开头的）。并发默认 4。单项上限 30 分钟，整轮上限 2 小时。
  用途：只给定时任务（建议每天一次），开发自测禁止跑 c 档。

--all 已退役：见到它直接退出 2 并指向 --ci / --full。三个选择互斥，不能与 --id 同给。

目录约定

- tests/*.gd：本层一层就是测试条目（条目里登记用例）。首个非注释行必须是 `extends TestScriptBase`，
  否则会被跳过，并在 stderr 报一行「跳过非测试脚本」。
- tests/cases/*.gd：条目里的用例脚本，一条用例一个文件，不会自己进任何档，由条目的 CASES 登记。
- tests/tools/：工具、夹具、预览脚本、测试基座 _test_script_base.gd 与入口 Autoload _test_entry.gd 全放这里。
  该目录任何档都不扫，改过它们的 API 要手工跑一次对应脚本或预览。

条目与用例

- 条目里的用例由 _run_cases() 在同一个进程里依次跑（省掉每条一次引擎启动）；一条用例红，整条条目红，
  日志里最后一条 SUITE_CASE 就是出问题的那条。
- 加用例只往 tests/cases/ 里加文件，再在对应条目的 CASES 里登记；加条目才在本层新建文件，条目数上限 32。
- 公共基座在 tests/tools/_test_script_base.gd（class_name TestScriptBase）：取图、存图、断言、运行目录都只有它那一份，
  新脚本一律 `extends TestScriptBase`。只许覆写 _capture_frame_count()（默认 3 帧）。
- 单跑一条用例：`python .engine.py --path . -- --test=res://tests/<条目>.gd --case=<用例名>`。

只做关系断言

- 关系：`a + b == c`；调过 func() 之后 `a == $CONST`；同一函数换参数的两次读数互印证；表与资产两端对得上。
- 静态对比（没有前提的 `a == $CONST`、size() == 6、逐行文案比对、布局坐标比对、图元数比对）不要写进测试：
  数据改了测试跟着改，等于没守东西。外观交给 tests/tools/ 里的预览脚本人工看。

预览脚本（出图用）

tests/tools/_*_preview.gd 不进任何档，要出图就直跑引擎：

```bash
python .engine.py --path . --audio-driver Dummy -- --test=res://tests/tools/_example_preview.gd --run-directory=<目录>
```

截图只该往自己的运行目录写；写回仓库会被下一轮 .engine_test.py 的脏工作区检查判红。

宿主与清场

默认宿主是编辑器可执行文件以项目运行模式直跑（带 editor 特性，不出包）；加 --export 才导出 debug 包跑到包里。
_test_entry.gd 在 test 或 editor 任一特性下放行；没有 --test= 的普通运行（F5 / 正式包）立刻 return。

- 入口在挂测试节点前先把自动起来的主场景从树上摘掉并释放；要验主场景本身的测试写 `const NEEDS_BOOT_SCENE := true`。
- 同一进程跑多条用例要自己清场：_run_cases() 在两条之间调 _reset_between_cases()（窗口尺寸、设置文件、存档目录、
  待启动的局），用例自己改过的全局状态要在这条用例结束时还原。顺序相关的红先调 CASES 顺序，不要改断言。
- 每次运行独占 .export/.test_<GUID>/：日志在 <条目>/<条目>.log，user:// 在 user_data/<条目>/，timings.csv 记逐项耗时；
  出包模式测完删包目录，只留日志。共享写入只有三处，别并跑：项目根 .godot（缓存为空或过期时才写）、
  引擎与导出模板目录（首次下载）、导出包目录。
- 跑完后工作区还有未提交文件（含未跟踪且未被 ignore）只报一行「错误：测试完毕后工作区存在未提交文件」
  并退出 1；全部通过时先打印「测试通过」再打总耗时。工作区干净时再查失效的 `.uid` / `.import` 伴生文件，
  全部列出并退出 1（嵌套的独立工程有自己的 `res://` 根，不参与检查）。
- 并发跑时相邻测试进程启动错开 2 秒：同时启动的多个引擎会一起建 Vulkan swapchain，显存吃紧的机器会随机报
  VK_ERROR_OUT_OF_HOST_MEMORY。b 档的 4 线程要在显存 ≥6G 的机器上跑，这是机器容量问题，不是用例回归。

耗时测量（--timing）

- timings.csv 的 seconds 是整个测试进程的墙钟，boot_ms 是 _test_entry.gd 挂测试节点前的启动段，两者相减是用例本体。
- boot_ms 中位数是机器忙不忙的信号：超过 6s 的那一轮不要拿来跟别的数字比。
- 并发收益由最慢的一项决定：一项与一批的耗时差距过半时，脚本会提示把各项耗时规划得接近些。

超限与裁剪

- 撞上限时先删该条目里最贵的用例（用例脚本留在 tests/cases/ 里，随时能接回来），再降仿真步数与人口规模；
  不要靠加并发或放松上限解决。
- 一条条目长期超预算、或断言已知红时，把它改名成 _ 开头（例如 tests/foo.gd → tests/_foo.gd）：
  它随即退出 b 档，仍会被 c 档跑到。提交信息里列出暂退 CI 的条目。
